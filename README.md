## 왜 기획 문서를 마크다운으로 관리하나

**1. 문서끼리 어긋나는 문제를 막기 위해서입니다.**
프리패스 때는 요구사항정의서 · 화면설계서 · 테스트케이스를 각각 다른 파일로 따로 썼습니다. 문서 하나하나는 갖췄지만, 한 곳을 고치면 다른 문서는 그대로 남아 층 표기 · 우선순위 · 음성 정책이 서로 달라졌습니다. 기획 문서가 여러 장일수록, 고칠 때마다 어디를 같이 고쳐야 하는지 찾는 게 가장 큰 일이었습니다.

**2. 개발자와 AI가 같은 문서를 바로 읽게 하기 위해서입니다.**
노션 · 구글 시트에 있던 바꾸 문서는 개발자가 매번 내보내서 AI 도구에 다시 넣어야 했습니다. 마크다운으로 깃허브에 두면 개발자는 필요한 문서만 AI 도구에 연결해 읽고, PM은 고친 내용을 커밋으로 바로 반영합니다. 무엇이 언제 왜 바뀌었는지도 커밋과 변경 기록에 남습니다.

## 어떻게 관리하나

- **문서를 ID로 엮습니다.** 요구사항(`REQ-C-02`) → 기능(`C-02-1`) → 정책(`P-03-01`) → 테스트가 서로의 ID를 가리킵니다. 저장소에서 ID 하나를 검색하면 관련 문서가 모두 나옵니다.
- **한 곳을 고치면 영향받는 문서를 바로 찾아 함께 고칩니다.** ID로 영향 범위를 찾고, AI 도구로 해당 문서들을 한 번에 반영한 뒤, 무엇이 바뀌었는지 변경 기록(CHANGELOG)에 남깁니다.
- **같은 내용은 한 곳에만 둡니다.** 규칙 · 기준값은 정책서에만 두고, 기능 명세서는 정책 ID로 가리킵니다. 화면 문구도 한 문서를 기준으로 삼습니다.
- **문서 역할을 나눕니다.** 요구사항 정의서 = 무엇을 / 기능 명세서 = 어떻게(진입 → 동작 → 조건 → 예외 → 결과) / 정책서 = 기준값 / 테스트케이스 = 무엇으로 확인하나.
