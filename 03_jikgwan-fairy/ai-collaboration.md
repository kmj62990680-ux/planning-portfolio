## 1. 일하는 방식

1. **요청은 문제로 준다.** "이 화면 만들어"가 아니라 "사용자가 몇 번 갔는지 세기 어렵다"처럼 문제를 주고, AI가 낸 안 중에서 고르거나 내 안으로 바꾼다.
2. **결정은 그날 바로 기록한다.** 결정 · 근거 · 실패를 마크다운 노트로 남기고, AI가 다음 작업 전에 그 노트를 읽게 했다. 대화가 바뀌어도 같은 기준으로 이어서 만들 수 있었다.
3. **도구는 근거로 고른다.** 오픈소스는 깃허브 스타 수 · 라이선스 · 설치 부담을 보고 고르게 했다.
4. **AI가 "됐다"고 해도 실제 토스 앱에서 내가 확인한다.** 크롬 시험 통과와 사용자가 보는 화면은 다를 수 있다.

## 3. 사례: 요청 → AI가 한 것 → 내가 정한 것

### 3-1. 경기 결과 자동 수집기

| 단계 | 내용 |
|---|---|
| 처음 | 이겼어요 / 졌어요를 사용자가 직접 고르는 방식 |
| 내 요청 | 날짜를 고르면 그 팀 경기만 열리고 결과가 자동으로 들어오게 |
| AI 의견 | 두 번째 버전으로 미루자 — 야구만 720경기, 남자농구 270경기라 손으로 옮길 수 없고, 수집 장치가 생기고, 출시가 늦어진다 |
| 내 결정 | **지금 넣는다.** 이 기능이 있어야 입력이 짧아지고 첫 방문에 판정까지 간다 |
| AI 첫 설계 | 매일 밤 한 번 공식 누리집에서 결과 · 순위를 읽어 파일로 공개, 앱은 열릴 때 그 파일을 읽음(앱 재검토 없이 갱신) |
| AI가 짚은 위험 | 사람이 옮기는 게 아니라 프로그램이 공식 누리집을 자동으로 읽는 것 → 누리집 약관 · 경기 기록 데이터베이스 권리의 회색 지대. 줄이는 조건: 공식 누리집만 · 적게 접속 · 출처 표시 · 문제 제기 시 중단 |
| 내 안 | 경기 일정을 미리 갖고 있다가 **"이 시간엔 무조건 끝나 있다"에 맞춰 가져오거나, 올라오면 바로 가져오기** (쿼터 시간은 정해져 있어도 정확한 종료 시각은 알 수 없으니까) |
| 결과 | 두 안을 합친 설계: 경기 시간대(오후 2시~자정)에 10분마다 확인하되, **시작 + 종목별 경기 길이(농구 2시간 · 배구 2시간 30분 등)가 지났는데 결과가 빈 경기가 있을 때만** 그 리그 누리집에 접속. 매일 새벽 전체 갱신. GitHub Actions(무료)로 돌리고 GitHub Pages로 공개 → [jikgwan-fairy-data](https://github.com/kmj62990680-ux/jikgwan-fairy-data). 위험 조건 "적게 접속"이 "끝났을 때만 접속"으로 더 좁혀졌다 |
| 데이터 출처 | 포털 순위를 쓰면 안 되냐는 내 질문에 AI가 포털 약관(자동 수집 금지)을 확인 → 각 리그 공식 누리집만 |
| 범위 | 처음엔 시즌 중인 농구 · 배구만. 지난 시즌 직관과도 비교하고 싶을 것이라 보고 **야구 · 축구 추가를 내가 결정** → 7개 리그 |
| 검증 | 수집 결과로 다시 계산한 승 · 패 · 무가 7개 리그 모두 공식 순위와 일치(예: KBL 77경기 = 공식 순위 승수 합 77). 결과를 일부러 지워 다시 채워지는지, 확인할 경기가 없으면 접속하지 않는지도 시험 |
| 출시 날 밤 | 예약 실행이 새 저장소에서 늦게 켜져, 직접 실행해 그날 배구 결과를 반영. 남자부 경기가 끝나는 시간에 맞춰 한 번 더 돌려 5세트 결과까지 반영 |

### 3-2. 판정 기준

| 단계 | 내용 |
|---|---|
| 처음 | 내 승률만으로 판정: 70% 이상 승리요정 · 55% 이상 행운 · 45% 이상 반반 · 30% 이상 아슬아슬 · 그 아래 패배요정 |
| 내 안 | **팀 시즌 승률과 비교해야 "진짜" 승리요정** — 원래 강한 팀 팬은 누구나 승리요정이 되기 때문 |
| AI가 한 것 | 기대 승률 계산 · 5단계 구간 · 3경기 미만 처리 구현 |
| 내 피드백 | 써 보니 "8승 3패인데 왜 보통이지?"라는 혼란이 생김 |
| 결과 | 같은 3승 1패라도 팀 성적에 따라 판정이 달라짐(예: 시즌 승률이 높은 팀 팬은 행운의 직관러 +10%p, 낮은 팀 팬은 승리요정 +48%p). 기준은 차별점이라 유지하고, 판정 아래 이유 문장을 넣기로 결정("팀이 원래 강해요. 딱 그만큼 이겨요") |

### 3-3. 입력 방식

| 단계 | 내용 |
|---|---|
| 내 지적 | 판정이 3경기부터라 **최소 세 번은 들어와야 결과를 본다** — 이 서비스의 가장 큰 약점 |
| 결과 1 | 첫 방문에 지금까지 간 직관을 한 번에 넣는 기능(14:35). 처음엔 승 · 패 숫자를 올리면 "직관 7번 · 승률 71%"처럼 미리 보여 줌 |
| 내 지적 | 몇 번 갔는지 세는 것 자체가 어렵다 |
| 결과 2 | 숫자 입력 → **지난 경기 목록에서 체크**("11월 19일 (목) vs 부산 KCC · 86:82 승"). 아래 버튼에 "3경기 넣고 판정 보기"처럼 고른 개수 표시, 이미 기록한 경기는 "기록함"으로 막음. 기록하기 화면에는 최근에 안 적은 경기 4개를 바로 펼침 |
| 내 지적 | 뒤로가기가 없어 불편하다 → 토스 밖 미리보기에서도 뒤로가기 줄 추가(토스 안에서는 토스 상단 바와 겹치지 않게 숨김) |

### 3-4. 디자인

| 단계 | 내용 |
|---|---|
| 내 요청 | 첫 화면이 아마추어 같다 → 리퀴드 글래스나 토스 느낌으로 바꿀 수 있는 오픈소스를 찾아 비교 |
| AI가 한 것 | 여러 UI 라이브러리를 "토스 안에서 어울리나 · 폰 화면 · 가벼움" 기준으로 비교, 토스 디자인 시스템(TDS) 추천 |
| 내 결정 | TDS 채택. 단 부품을 그대로 쓰니 평범해 보여서, 핵심 화면(팀 카드 · 최근 직관 · 종목 고르기)은 직접 그리게 함 |
| 캐릭터 | AI가 낸 별 요정 안은 내가 탈락시킴 → Gemini로 4가지(병아리 · 날개 달린 티켓 · 빛 요정 · 꼬마 요정) 비교 → **티켓 요정 선택**(직관 = 티켓, 판정을 티켓 상태로 표현). 그림은 내가 Gemini로 뽑고, AI가 잘라 배경을 지움 |
| 로고 | 밋밋함 → 요소 과다 → 바탕색 4개 비교 → 가운데 기호 비교(왕관) 순서로 좁힘. 160 · 96 · 48px로 줄여 가장 작은 크기에서도 읽히는지 확인. 티켓 오른쪽 파란 절취선이 바탕과 겹쳐 보인다는 **내 지적으로 아이보리 바탕으로 변경** |
| 강조 | 판정 차이(+N%p)만 강조돼 있다는 내 지적 → 아래 점수 줄(직관 수 · 결과 · 내 승률)도 같은 글꼴 · 승률 색으로 |
| 글꼴 | 후보 6개를 판정 화면에 대 보고 선택. 라이선스(앱 포함 시 원본 수정 금지 · 전문 포함)를 확인하고 원본 그대로 넣음 |
| 파일 크기 | 글꼴 · 고해상도 그림을 넣을 때마다 크기를 확인(약 1.3MB → 2.1MB → 3.4MB → 6.4MB, 한도 100MB), 쓰지 않는 아이콘 12개 삭제 |

### 3-6. QA

| 단계 | 내용 |
|---|---|
| 내 요청 | "QA 해 봐, 스타 많은 오픈소스로" |

## 4. AI 결과를 그대로 쓰지 않은 곳

- **AI 예상이 틀린 곳:** 작은 아이콘은 이모지 글꼴이 낫다는 판단 → 실제 크기(16~28px)로 넣어 보니 3D 그림이 더 잘 읽혀서 바꿈.
- **"시험 통과"와 실제 화면이 다른 곳:** 승률 카드는 크롬 · 아이폰 엔진 시험을 통과했지만 토스 앱 안에서는 캐릭터가 빠졌다. 실제 기기 확인 없이 출시했으면 놓쳤을 문제.
- **데이터:** 수집 결과를 공식 순위와 대조해 일치를 확인한 뒤에만 공개.
