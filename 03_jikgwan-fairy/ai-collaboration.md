# PM과 AI의 역할 분담

> 무엇을 왜 만들지는 PM이 정하고, 구현은 AI에게 맡겼다.
> 그 결과 첫 버전부터 출시까지 하루(2026.11.24)가 걸렸다.

## 1. 역할

| PM (나) | AI (Claude Code) |
|---|---|
| 문제 정의, 판정 기준 설계 | 화면 · 기능 구현 |
| 기능 범위와 우선순위 결정 | 경기 결과 수집기 구현 |
| 사용자 흐름 점검, 실제 기기 검증 | 자동 시험 작성 · 실행 |
| 지표 설계, 출시 판단 | 자료 조사, 도구 비교 |

## 2. PM이 내린 핵심 판단

### 판정 기준을 바꿨다
처음 판정은 내 승률만 봤다. 그러면 강팀 팬은 누구나 승리요정이 된다.
**팀 시즌 승률과 비교하는 방식**으로 바꿨고, 이것이 서비스의 차별점이 됐다.

### "세 번 와야 결과를 본다"는 문제를 찾았다
판정은 3경기부터라, 매번 하나씩 기록하면 첫 결과까지 세 번 와야 한다.
**첫 방문에 지난 직관을 한 번에 넣는 기능**을 만들었고, 숫자 입력 대신 **경기 목록에서 체크**하게 바꿨다.

### AI가 미루자던 기능을 1차에 넣었다
AI는 경기 결과 자동 반영을 다음 버전으로 미루자고 했다. 7개 리그 시즌 경기가 약 1,800개라 손으로 옮길 수 없다는 이유였다.
입력이 짧아야 첫 방문에 판정까지 간다고 보고 **이번 버전에 넣기로 결정**했다.
수집 방식도 직접 제안했다. 경기 일정을 미리 알고 있으니 **"이 시간이면 반드시 끝나 있다"는 시점에만 확인**하면 된다. 이 설계로 불필요한 접속 없이 결과를 반영한다.

### 대표 지표를 바로잡았다
처음 후보는 승률 카드 공유였다. 콘솔에서 대표 지표가 전환율 계산에 쓰인다는 것을 확인하고, 사용자가 가치를 받는 순간인 **직관 기록**으로 바꿨다.

## 3. AI 결과를 그대로 믿지 않았다

- **실제 기기 검증:** 승률 카드는 자동 시험을 통과했지만, 토스 앱에서 직접 확인하니 캐릭터가 빠져 있었다. 원인을 좁혀 출시 당일 해결했다.
- **데이터 대조:** 수집한 결과로 계산한 승패를 7개 리그 공식 순위와 대조해 모두 일치하는 것을 확인한 뒤 공개했다.
- **출처 판단:** 포털 데이터 대신 리그 공식 누리집만 쓰기로 정했다. 포털 약관이 자동 수집을 금지한다.
