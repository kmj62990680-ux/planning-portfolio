# 만든 과정 · AI와 일한 방식

> 이 문서는 서비스 기획 문서가 아니라 **만든 사람이 AI와 어떻게 일했는지**를 적은 기록이다. 서비스 자체는 [README](README.md)의 기획 문서를 보면 된다.

| 항목 | 값 |
|---|---|
| 기간 | 2026-11-24 ~ 2026-11-25 (기획 · 개발 · QA · 출시 · 운영 대응) |
| 도구 | Claude Code(조사 · 개발 · 시험 · 수집기), Gemini(캐릭터 · 로고 그림), GitHub Actions · Pages(수집기 실행 · 데이터 공개) |
| 나눈 선 | 코드 · 조사 · 시험 실행 · 초안은 AI / 무엇을 만들지 · 기준 · 실제 기기 확인 · 출시 판단은 PM(나) |

## 1. 일하는 방식

1. **요청은 문제로 준다.** "이 화면 만들어"가 아니라 "사용자가 몇 번 갔는지 세기 어렵다"처럼 문제를 주고, AI가 낸 안 중에서 고르거나 내 안으로 바꾼다.
2. **결정은 그날 바로 기록한다.** 결정 · 근거 · 실패를 마크다운 노트로 남기고, AI가 다음 작업 전에 그 노트를 읽게 했다. 대화가 바뀌어도 같은 기준으로 이어서 만들 수 있었다.
3. **도구는 근거로 고른다.** 오픈소스는 깃허브 스타 수 · 라이선스 · 설치 부담을 보고 고르게 했다.
4. **AI가 "됐다"고 해도 실제 토스 앱에서 내가 확인한다.** 크롬 시험 통과와 사용자가 보는 화면은 다를 수 있다.

## 2. 사례: 요청 → AI가 한 것 → 내가 정한 것

### 2-1. 경기 결과 자동 수집기

| 단계 | 내용 |
|---|---|
| 내 요청 | "날짜를 고르면 그 팀 경기만 열리고 결과가 자동으로 들어오게" (처음엔 이겼어요 / 졌어요를 직접 고르는 방식이었다) |
| AI 의견 | 두 번째 버전으로 미루자고 제안 |
| 내 결정 | **지금 넣는다.** 입력이 짧아야 첫 방문에 판정까지 간다 |
| 내 요청 | "경기가 끝날 때마다 계속 불러올 수 없나" |
| AI 의견 | 경기마다 계속 접속하는 방식의 위험을 설명 |
| 내 안 | **일정을 미리 갖고 있다가 "이 시간엔 무조건 끝나 있다"에 맞춰 가져오거나, 올라오면 바로 가져오기** |
| 결과 | 두 안을 합친 설계: 시작 시간 + 종목별 경기 길이가 지났는데 결과가 빈 경기가 있을 때만 그 리그를 확인(10분 간격), 매일 새벽 전체 갱신. GitHub Actions(무료)로 돌리고 GitHub Pages로 공개 → [jikgwan-fairy-data](https://github.com/kmj62990680-ux/jikgwan-fairy-data) |
| 데이터 출처 | 포털 순위를 긁자는 내 질문에 AI가 포털 약관(자동 수집 금지)을 확인 → 각 리그 공식 누리집만 쓰기로 정함 |
| 범위 | 처음엔 시즌 중인 농구 · 배구만. "지난 경기와도 비교하고 싶을 것"이라 보고 **야구 · 축구 추가를 내가 결정** → 7개 리그 |
| 검증 | 수집 결과로 다시 계산한 승 · 패 · 무가 7개 리그 모두 공식 순위와 일치하는 것을 확인하고 공개 |

### 2-2. 판정 기준

| 단계 | 내용 |
|---|---|
| 처음 | 내 승률만으로 판정(70% 이상 승리요정 등) |
| 내 안 | **팀 시즌 승률과 비교해야 "진짜" 승리요정** — 원래 강한 팀 팬은 누구나 승리요정이 되기 때문 |
| AI가 한 것 | 기대 승률 계산 · 5단계 구간 · 3경기 미만 처리 구현 |
| 내 피드백 | 써 보니 "8승 3패인데 왜 보통이지?"라는 혼란이 생김 |
| 결과 | 기준은 차별점이라 유지하고, 판정 아래 이유 문장을 넣기로 결정("팀이 원래 강해요. 딱 그만큼 이겨요") |

### 2-3. 입력 방식

| 단계 | 내용 |
|---|---|
| 내 피드백 | "몇 번 갔는지 세는 것 자체가 어렵다" |
| 결과 | 승 · 패 숫자를 넣는 방식 → **지난 경기 목록에서 체크하는 방식**으로 교체. 기록하기 화면에는 최근에 안 적은 경기 4개를 바로 펼침 |

### 2-4. 디자인

| 단계 | 내용 |
|---|---|
| 내 요청 | 첫 화면이 아마추어 같다 → 깃허브에서 많이 쓰는 UI 라이브러리를 찾아 비교 |
| AI가 한 것 | 여러 UI 라이브러리를 "토스 안에서 어울리나 · 폰 화면 · 가벼움" 기준으로 비교, 토스 디자인 시스템(TDS) 추천 |
| 내 결정 | TDS 채택. 단 부품을 그대로 쓰니 평범해 보여서, 핵심 화면(팀 카드 · 최근 직관 · 종목 고르기)은 직접 그리게 함 |
| 캐릭터 | AI가 낸 별 요정 안은 내가 탈락시킴 → Gemini로 4가지(병아리 · 날개 달린 티켓 · 빛 요정 · 꼬마 요정) 비교 → **티켓 요정 선택**(직관 = 티켓, 판정을 티켓 상태로 표현). 그림은 내가 Gemini로 뽑고, AI가 잘라 배경을 지움 |
| 로고 | 밋밋함 → 요소 과다 → 바탕색 4개 비교 → 가운데 기호 비교(왕관) 순서로 좁힘. 파란 바탕에서 티켓 절취선이 묻히는 걸 보고 **아이보리 바탕을 내가 제안** |
| 글꼴 | 후보 6개를 판정 화면에 대 보고 선택. 라이선스(앱 포함 시 원본 수정 금지 · 전문 포함)를 확인하고 원본 그대로 넣음 |

### 2-5. 기획 검증

| 단계 | 내용 |
|---|---|
| 내 요청 | 기획을 검증해 주는 오픈소스로 빈 곳을 보자 |
| AI가 한 것 | YC 오피스아워식 검증 질문 틀(gstack `office-hours`)을 설치 없이 가져와 적용, 빈 곳 8개를 심각한 순으로 정리 |
| 결과 | 판정 기준 · 입력 부담 · "승률이 두 개라 헷갈림"을 출시 전에 풀고, 남은 것(재방문 이유)은 다음 개선 1순위로 |

### 2-6. QA

| 단계 | 내용 |
|---|---|
| 내 요청 | "QA 해 봐, 스타 많은 오픈소스로" |
| AI가 한 것 | Playwright(흐름) · axe-core(접근성) · Lighthouse(속도)로 시험 21개 작성 · 실행, 대비 부족 7곳 등 수정 |
| 내가 찾은 것 | 기록이 생기면 "한 번에 넣기" 버튼이 사라지는 문제 · 토스 앱에서 승률 카드가 저장 안 되거나 캐릭터가 빠지는 문제 |
| 반복 | 카드 문제는 크롬 시험을 통과했는데도 토스 앱에서 다섯 차례 확인 → 결국 카드를 캔버스에 직접 그리는 방식으로 바꿔 해결 |
| 결과 | 같은 시험을 아이폰 엔진(WebKit)으로도 돌리게 바꿔 42개 전부 통과 |

### 2-7. 지표

| 단계 | 내용 |
|---|---|
| AI 제안 | 승률 카드 저장 · 공유를 대표 지표로 |
| 내 확인 | 콘솔 화면에서 대표 전환이 전환율 계산에 쓰인다는 것을 확인 |
| 결과 | 대표 전환을 "직관 기록"으로 바꿈(사용자가 가치를 받는 순간). 활성 지표는 7일 이후 재방문 |

### 2-8. 출시 다음 날 수집기 멈춤

| 단계 | 내용 |
|---|---|

## 3. AI 결과를 그대로 쓰지 않은 곳

- **AI 예상이 틀린 곳:** 작은 아이콘은 이모지 글꼴이 낫다는 판단 → 실제 크기(16~28px)로 넣어 보니 3D 그림이 더 잘 읽혀서 바꿈.
- **"시험 통과"와 실제 화면이 다른 곳:** 승률 카드는 크롬 · 아이폰 엔진 시험을 통과했지만 토스 앱 안에서는 캐릭터가 빠졌다. 실제 기기 확인 없이 출시했으면 놓쳤을 문제.
- **데이터:** 수집 결과를 공식 순위와 대조해 일치를 확인한 뒤에만 공개.
